# 产品匹配与工作流核验

目的是帮助主要使用 Skill 的开发者和 AI 实践者判断“现有项目能否帮助目标产品用户，在相近场景下完成同一件事”，并解释产品边界。开发者和 AI 实践者是服务定位，不是每次请求的固定用户或检索过滤条件。Skill 使用者（提出 idea、构建 Skill/产品的人）与被分析项目的最终用户是两层角色，必须分别记录；实际请求者未知时明确标注。关键词、技术栈和 GitHub stars 都不能替代这个判断。普通自然语言需求和复杂技术选型都适用；不要把所有任务扩展成商业市场分析。先用一句话说明目标产品用户要完成的任务，再用项目卡片回答“谁在什么场景解决什么问题、怎样完成、结果是什么”；实现细节只保留会改变选择的证据。

## 统一星级

展示用 `⭐️⭐️⭐️⭐️（4/5）`，整数 1–5，不用高中低、半星、小数或百分比。每个分数附一句具体依据。星级是有依据的序数判断，不是算法准确率或 GitHub stargazers。证据不足、用户未指定技术基线时用 `❔未确认`，不能给一星代替未知。

| 星级 | 产品匹配 | 功能覆盖 | 技术匹配（仅技术基线明确时） |
|---|---|---|---|
| 5 | 同类用户、核心问题、必要工作流和结果高度一致；无已知关键冲突 | 所有已明确的必要能力均有依据支持 | 关键数据流、架构接口及用户要求的技术约束一致 |
| 4 | 核心用户任务一致，存在明确但不阻断主要用途的产品边界差异 | 主要能力覆盖，少量补充能力缺失或需适配 | 主要实现路径一致，局部需要适配 |
| 3 | 相同问题的一部分，或用户/场景/工作流存在明显差别 | 核心能力有实质重合，但缺少重要阶段 | 部分数据流或模块可对照，但关键实现不同 |
| 2 | 相邻问题、不同最终用途，仅能借鉴某环节 | 仅一两个局部能力重合 | 只共享局部机制或组件，整体方案不同 |
| 1 | 有证据表明关联很弱，仅概念邻近 | 已观察能力与需求几乎不重合 | 已知实现与技术基线几乎不重合 |

不对三项求平均。产品星级决定主要推荐顺序；功能星级说明覆盖，技术星级说明实现接近程度。共享 Python 或“都用 AI”不足以给出技术高星。关键必需项冲突应降低产品匹配并写出原因。只有文档声明时明确标为文档依据，不能暗示已运行验证。

## 源码阅读服务于用户工作流

对最值得推荐的直接匹配项目，以及决定排序的争议候选，检查影响产品匹配的关键步骤。优先 1–3 个项目，按信息增益扩展；不对每个候选进行全仓库审计。

1. 把用户工作流拆成可观察步骤：触发/入口 → 输入处理 → 状态变化或存储 → 输出/后续操作。阶段按实际场景选择，不强加任务执行或自动化。
2. 从项目入口追到相关处理函数、状态保存和输出接口。只找到命名相似的函数、类型定义或 UI 按钮不等于流程已连通。
3. 对每个影响判断的步骤记录“源码观察 / 文档声明 / 未确认”，并附路径、行号、调用关系及对应 URL。静态观察不能写成运行成功。
4. 将“自动、实时、本地优先、后台同步、闭环”等关键描述落到具体行为：触发条件是什么、数据保存在哪里、下一步由谁启动、是否需要额外服务。找不到证据写未确认，不直接写不存在。
5. 需要时通过 GitHub Contents、原文件或已有本地 checkout 阅读；API 限流时可使用公开仓库的浅克隆。先读取文件清单、再定位少量文件。仅阅读，不为核验自动安装依赖或运行候选程序。
6. 记录核验版本与范围。Git 克隆读取应附公开文件链接和 commit；不能仅说“已经克隆源码”。

`github_discover.py` 提供候选、代码搜索命中和元数据；实际工作流追踪由 Agent 阅读文件完成。两者不能混称为脚本自动验证完整流程。按需读取测试辅助理解边界，也要区分测试代码存在和测试实际通过。

## 多角度检索与增量发现

查询需要覆盖至少两个对当前问题有意义的角度，例如用户痛点/结果、工作流的输入与动作、功能机制、项目类别/Topics、关联项目。角度不是信息源：多个仓库查询也可覆盖多个产品角度，但不能因此声称执行了 Code Search 或向量检索。

- 不预设 stars 下限，不先按热度选择深读项目。低 star 项目不等于好项目，也不等于“隐藏宝藏”。
- 查询返回量远超取样上限且前排大量无关时，收窄到任务词或确切短语；太少时换同义表达或沿相关项目扩展。不能将几十万条命中的前 20 条当作全面覆盖。
- 相关项目可能来自不同用户用语、Topics、Awesome Lists 或源码/Issue 线索；按证据再次确认产品工作流后才推荐。
- 目前脚本没有向量索引；Agent 的语义理解与重排不等于独立语义召回引擎，不宣称已实现后者。

只有保留对照查询记录时才描述“本轮增量发现”。例如：“首轮指定关键词检索的前 20 条未出现，通过 topic:github-search 找到并核验。”记录基线查询、取样上限、发现路径；这不是“普通搜索永远搜不到”的证明。

没有对照时，只写“值得关注的小型项目”或具体发现来源。对外能力可表述为“通过多角度检索，补充单一关键词检索容易遗漏的候选”；效果优于普通搜索的广泛承诺需要内部基准支持，正常用户无需做评测。

## 比较竞品时保持事实边界

从产品定位、目标用户、工作流和可观察实现比较。不能根据一段简介断言对方“没有产品意识”，不能把对方已有的意图解析或源码核验说成我们的独有优势。把我们希望强调的产品维度称为设计侧重点，是否构成优势取决于实际报告能否持续提供这些信息。
